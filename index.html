This is the core reason warehouses exist. The two workloads fight each other. Separate them and both get faster. The grids show why warehouses are fast: a query like total order value only needs one column. A row store reads whole rows to get it; a column store skips everything else. 02 · ETL vs ELT

Two ways to copy data out of an app

Batch

App DB

Every few hours

Data lake

Copy tables on a schedule

Simple, but the data is hours old

Use when hours-old data is fine

CDC

App DB

Every change, in seconds

CDC stream (Kafka)

Data lake

Stream every change

Inserts, updates and deletes flow as a stream other services can also read

Use when minutes matter

Zomato runs both, choosing per pipeline: batch where hours-old data is fine, CDC where freshness matters.

CDC = change data capture. It reads the database's own change log instead of querying tables, so it barely touches the production database. Analogy: batch is photocopying the ledger every night; CDC is a ping for every new line written. At Zomato (2023), batch was Sqoop jobs into S3, and CDC was Debezium into Kafka, processed by Flink. The CDC stream is a Kafka topic per table: each change is an event, kept in order, and the lake is just one reader. Other services (search, caches, real-time features) can read the same stream.

1 · Why events

How we got here: monolith → microservices → events.

STEP 1

Monolith

One app and one database: orders, payments, email and reports together.

Good: simple to start.

Problem: one change redeploys everything; one bug can take it all down.

→
STEP 2

Microservices

Small services (order, payment, email), each owned by a team, calling each other's APIs.

Fixes: teams deploy and scale independently.

New problem: services wait on each other; one slow service blocks the rest.

→
STEP 3

Event-driven

Services announce what happened (an event) to a broker. Others react in their own time.

Fixes: no waiting, failures contained, new consumers just subscribe.

Cost: data is consistent a moment later; debugging is harder.

You already use events every day

GitHub webhookYou push code; GitHub calls your CI and the build starts.
Payment webhookRazorpay or Stripe calls your API when a payment succeeds.
Browser eventsaddEventListener('click', …) runs your code when the user clicks.
Spring listeners@EventListener or @KafkaListener runs a method when an event arrives.

Event-driven architecture is the same idea across services, with a broker in the middle so many services can listen and nothing is lost while one is down.

Start from what everyone already uses: a webhook is an event pushed over HTTP. Each step fixed the previous step's main problem and introduced a new one. Microservices solved the "one big app" problem but created a web of direct calls. Events solve the web of calls.

1 · Why events

The shift: announce, don't call. So what is an event?

Definitions

Event-driven architecture: a design where services communicate by publishing events to a broker; other services subscribe and react on their own, instead of calling each other directly.

Event: an immutable record of something that already happened, e.g. OrderPlaced.

Order serviceproducer
OrderPlaced
Brokerstores the event
Payment
Inventory
Email
Fraud check new
Producer states a fact; whoever cares, listens. The fraud team subscribes next month with zero change to the order service.

Command vs event

Command ChargeCard: "please do this". One receiver; it can be rejected.

Event PaymentCompleted: "this happened". Past tense, can't be changed, any number of listeners.

What an event looks like

{ "eventType": "OrderPlaced",
  "eventId":   "e7f1-42c9",
  "occurredAt": "2026-11-17T10:42:00Z",
  "data": { "orderId": "1042", "amount": 899 } }
The core change: stop calling everyone, announce the fact once. An event is past tense and immutable; a command is a request to one receiver.
1 · Why events

The trade-off: what you gain, what you pay.

You gain

  • Loose coupling
  • Resilience to failures
  • Absorbs traffic spikes
  • Easy to add new features
  • Independent scaling
  • Replayable history (with a log)

You pay

  • Eventual consistency
  • Harder debugging (needs tracing)
  • Duplicate and out-of-order events
  • Schema contracts between teams
  • A broker to run and monitor
  • Harder end-to-end testing
Skip events when the caller needs the answer right now (login, stock check, payment approval) or the app is small.
Debate corner

Are microservices always better? Prime Video (2023) moved one monitoring tool back into a single app and cut its cost by about 90%.

Walk the two lists, then open the debate. There's no universal answer: microservices and events pay off with many teams and real scale; a small team often moves faster with a well-structured monolith. Definitions

Pub/sub: each message is pushed to every current subscriber.

Log: messages are appended and kept; each consumer tracks its own position and can re-read.

Definition

Apache ActiveMQ: an open-source, Java-based message broker that implements JMS (Java Message Service), the standard messaging API for Java applications. It offers queues (one consumer) and topics (pub/sub).

Definition

Apache Kafka: an open-source, distributed event streaming platform that stores events in an ordered, replicated log. Producers append events; any number of consumers read them at their own pace and can re-read them.

Producer

An app that writes events to a topic (e.g. order service). Sends in batches; doesn't know who reads.

Consumer

An app that reads events (e.g. billing). Pulls at its own pace; reading deletes nothing.

Broker

One Kafka server. Stores partitions and serves producers and consumers. Several brokers form a cluster.

Record (event)

One message: a key, a value (the data), a timestamp and optional headers.

Topic

A named stream of related events, e.g. orders. Like a table name for events.

Partition

A slice of a topic: an ordered, append-only log. Spread across brokers so work runs in parallel.

Offset

An event's position number in its partition (0, 1, 2…). Consumers use it as a bookmark.

Key

Decides the partition. Same key (order 1042) → same partition → its events stay in order.

Each event has a key; the producer hashes it to pick a partition, so all events for one order stay in sequence. A hot key creates a hot partition, so choose keys that spread evenly.

5 · Production

Delivery guarantees: lose, duplicate, or neither?

Definition

Delivery guarantee: how many times a message may be processed when something fails: at most once (may lose), at least once (may duplicate), or exactly once (in effect).

At-most-once

Commit → then process. A crash after commit = the message is lost. Never duplicated.

In apps: Hotstar live viewer count, "typing…" in chat, click analytics. A missed event doesn't matter.

At-least-once

Process → then commit. A crash before commit = processed again. Never lost.

In apps: Swiggy order SMS, Uber trip receipt, BookMyShow ticket. Never lose it; dedupe repeats.

Exactly-once

Idempotent producer + transactions. Kafka-to-Kafka pipelines only; costs some throughput.

In apps: PhonePe cashback totals, ad-click billing, seller payout totals. Counting twice costs money.

Practical recipe: at-least-once delivery + an idempotent consumer (skip an event whose ID you've already processed) = effectively exactly-once, across any system: database, API, email.
The choice is about when the consumer commits its offset. The practical answer for payments: at-least-once plus deduplication by event ID.

Four very different readers consume the same data: Flink for live computation like surge, Pinot for sub-second dashboards, the Hadoop data lake for batch and ML (Part 1's world), and microservices through the consumer proxy for queue-style work with retries and a DLQ. One log, many readers.

Appendix · Kafka deep dive

Consumer groups: share the work, or get your own copy.

Definition

Consumer group: a set of consumers sharing one group ID that split a topic's partitions between them, so each event is processed once per group; every other group receives all events too.

stable · 3 consumers
group: analytics
A1reads all partitions

Another group gets every event again, with its own offsets.

topic: orders · 6 partitions
group: billing

The rules

  • In a group, each partition goes to one consumer.
  • More consumers than partitions → extras sit idle.
  • A consumer joins or leaves → partitions are rebalanced.
  • Offsets are saved in Kafka, so a restart resumes where it stopped.

When to use them

  • Scale one app: 6 pods join group order-processor and split the partitions.
  • Many apps, same data: billing, analytics, notifications each use their own group.
  • Plan partitions for peak consumers.
Add consumers to seven: one sits idle with six partitions. Crash one: its partitions move to the others. The analytics group never notices.
Appendix · Kafka deep dive

A cluster of brokers: never trust one disk.

Definition

Replication: Kafka keeps copies of each partition on several brokers. One copy, the leader, handles all reads and writes; the others, followers, copy it. Followers that are fully caught up form the ISR (in-sync replicas).

Broker 1P0 · leaderP1 · followerP2 · follower
Broker 2P0 · followerP1 · leaderP2 · follower
Broker 3P0 · followerP1 · followerP2 · leader
Leaders are spread so the load is shared; followers keep copying their leader. Lose any one broker and no data is lost.

Three settings that matter

  • replication.factor = 3: keep 3 copies of every partition, on 3 brokers.
  • acks = all: the producer waits until all in-sync copies have the event.
  • min.insync.replicas = 2: refuse writes if fewer than 2 copies are up to date. Safer to pause than to lose data.

ISR (in-sync replicas) = the followers that are fully caught up with the leader. Production clusters usually start with 3 brokers.

A broker is one Kafka server; a cluster is several working as one. Each partition has a leader that handles reads and writes and followers that copy it.
Appendix · Kafka deep dive

Leader election: who takes over when a broker dies?

Definition

Leader election: when the broker holding a partition's leader fails, Kafka's controller automatically promotes an in-sync follower to be the new leader, so reads and writes continue.

1Broker 1 goes silentIt was the leader for P0. Its heartbeats stop.
2Controller noticesKafka's built-in controller (KRaft) sees the broker is gone.
3New leader from the ISRIt picks an up-to-date follower, e.g. Broker 2.
4Clients redirectProducers and consumers refresh and carry on, usually within seconds.

Why only the ISR?

Only a fully caught-up copy can lead without losing data that was already confirmed.

Unclean election: off

By default Kafka prefers a short outage over promoting an out-of-date copy.

Goodbye ZooKeeper

Kafka 4.0 (2025) removed ZooKeeper. The controller now runs inside Kafka (KRaft).

Walk the four steps. The safety rule: a new leader must be in sync, otherwise acknowledged data could vanish.

Appendix · Kafka deep dive

Disks cost money: classic, tiered and diskless Kafka.

Classic (disk-based)

Data on each broker's local disk, copied broker to broker.

+ Lowest latency (milliseconds)
− Brokers hold data, so scaling means moving data; copies between cloud zones cost money

Tiered storage

Recent data on disk, older data moved to S3. Production-ready since Kafka 3.9 (2024).

+ Cheap long retention
− Active data is still copied between disks

Diskless

Brokers write straight to object storage (S3) and keep no data.

+ Cheaper, elastic, no cross-zone copying
− Higher latency (hundreds of milliseconds)

Status (Nov 2026): KIP-1150 "Diskless Topics" was accepted in March 2026 but isn't in an Apache Kafka release yet. Available today from WarpStream, Aiven Inkless and others.
Rule of thumb: latency-critical (payments, fraud) → classic. High-volume logs, telemetry, analytics → diskless.

Also new: Kafka 4.0 removed ZooKeeper (KRaft); Kafka 4.2 added queue-style "share groups".

Three storage models, one trade-off: latency vs cost. Diskless lets the object store handle durability so brokers become stateless.
